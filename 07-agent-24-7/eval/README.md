# eval

Eval пакета 07 — не вопросы к модели, а сценарии сбоев с известным исходом: каждая задача либо доставлена, либо лежит в dead-letter с причиной, либо потеряна.

- **Ночь по умолчанию** (`Night()` в `src/razbor07/sim.py`, seed 48): 1 000 вопросов от 60 магазинов за 4 часа, 30 % — в 10-минутный утренний пик. Модель: задержка — логнормальная, медиана 3 с; лимит 50 запросов в минуту на ключ (сверх — 429 с retry-after); перегрузка 529 — 1 % вызовов; зависание — 0,5 %; обрыв посреди ответа — 1 %; битая задача (400 на каждый вызов) — 0,5 % задач. Процесс с агентом получает kill -9 в среднем раз в 30 минут и поднимается за 5 с. 1 % ответов API клиенту теряется; клиент ждёт до 60 с и переспрашивает один раз.
- **Сбои по одному** (`PROFILES` в `src/razbor07/experiment.py`): каждый сбой отдельно на той же тысяче задач, плюс ночь без сбоев.
- **100 ночей**: seed 1000–1099, все сбои вместе.
- **Что меряется** для каждой конфигурации: доставлено; потеряно (ответа нет, в dead-letter нет); дубли (магазин получил ответ дважды и больше); в dead-letter; p50/p95/p99 от первого запроса клиента до письма (виртуальные секунды, по доставленным); трасса до конечного статуса (у каждой начатой попытки есть событие, которым она кончилась); вызовы модели на доставленный ответ; отказы 429; kill -9.

## Критерий «прошёл»

Для конфигурации «прод» в каждом профиле и в каждой из 100 ночей:

1. Потеряно — 0.
2. Дублей — 0.
3. Доставлено + dead-letter без ответа = все задачи; в dead-letter без ответа — только битые задачи (`dead_exhausted` = 0). Бывает, что в dead-letter попадает задача, письмо по которой уже ушло: последний вызов модели исчерпал 6 попыток в пике 429. Магазин ответ получил, задача видна оператору, возврат в очередь второго письма не отправит.
4. Трасса до конечного статуса — у всех задач.

Проверяют `tests/test_experiment.py` (ночь и профили) и прогон `uv run razbor07 all` (100 ночей: `nights.summary.prod.nights_with_lost` и `nights_with_dup` = 0).
